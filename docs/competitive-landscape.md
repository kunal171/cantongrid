# CantonGrid: ecosystem overlap, differentiation and implementation status

**Research snapshot:** 2026-11-17 (UTC). **Status:** comparative research and technical recommendations, not a change to the accepted release scope. Read alongside [product](product.md), [decisions](decisions.md), [roadmap](roadmap.md) and [verification](verification.md). Product or proposal status can change; recheck linked primary sources before making a grant claim.

## Executive finding

CantonGrid's first release is an **authorized, Daml-first, application-configurable indexing system**, with Outcomia as its first example and an unrelated second example as a generality test. A future multi-source/track framework remains the long-term vision, but public Scan, assets and operator/governance tracks are **not part of the currently accepted first release** (D-001 and D-006).

The generic claim "Rust indexer that reads PQS, generates PostgreSQL projections and APIs" has **high overlap** with other funded/proposed Canton infrastructure. It is not credible to claim that CantonGrid is Canton's first indexer, the only permission-aware indexer, or the first public/private data solution. The potential contribution must be shown through **measurable developer-configured processing, policy-derived data access, provenance/completeness contracts, and demonstrated reusability**, ideally complementing existing sources and indexers.

Neither these design hypotheses nor this research establish that CantonGrid is already faster, safer, more complete or production-ready.

## Claims CantonGrid must not make

- "The first Canton indexer", "no open indexer exists", or "the only privacy-preserving indexer".
- "Rust, PQS access, configurable filters, PostgreSQL materialization, API generation, GraphQL or streams make us unique." These features exist or are already proposed.
- "Public Scan + private contracts is an original architecture." Zpoken proposes it and Canton Index's next phases include Scan.
- "Every returned result is complete" or "we can index the entire Canton network". Visibility and historical retention are source- and grant-limited.
- "Noves is completely open source"; the observed public product repository primarily distributes deployment materials for packaged images.
- "Canton Index is only a proposal with no executable"; Cinder and the indexer server have released binaries/images.
- "Proposed, fixture-tested, LocalNet-tested and production" as interchangeable maturity labels.
- "Faster", "safer", "exactly once", or "zero-config for any Daml package" without explicit evidence and defined limits.

## Technical differentiation hypotheses to prove

**H1 — Deterministic application-level models, not just per-row filters.** For supported vocabulary, users declare selections, typed output, source lifecycle dependencies, derived calculations and relationships; the engine produces storage, migrations, authenticated query interfaces and resumable changes without handwritten application-specific Rust/SQL/resolvers. This overlaps Canton Index's future stateful phase, so compare concrete capabilities and timelines. Proof: Outcomia plus an unrelated Daml model, no engine edits, snapshot/replay equivalence, archive retractions and controlled schema upgrades. **Planned, not implemented.**

**H2 — Authorization is a transitive dependency of derived data.** Source credentials do not authorize API consumers. A result derived from A-only and B-only private inputs cannot be made accessible to A-only or B-only users through counts, joins, cache, errors, GraphQL, SSE or replays. Authorization epochs, source health and grant revocation must fail closed. Proof: A/B/AB scope tests across all serving paths, including previously materialized and streamed outputs. Rust decision primitives and fixtures already cover part of this; authenticated live APIs remain unbuilt.

**H3 — Machine-readable source provenance and completeness at query boundaries.** Reports must expose what source and scope they cover; snapshot versus partial history; known gaps, pruning and earliest available history; checkpoint/freshness; schema/processing version; and a reason when coverage is unknown. Never promote a source-local offset to a universal global order. Proof: one query producing `PARTIAL_HISTORY` on a pruned input, a strict authorization-scoped cursor, and a mixed-source test that refuses a false complete total. Note: Noves #949 proposed related coverage/evidence, so distinguish **specific, reusable enforcement** rather than claiming invention of provenance. Contracts-first first-release metadata is in scope; mixed-source implementation is future work.

**H4 — Source/track independence as an extensible future contract.** Keep source acquisition and downstream processing separate; a future public Scan track should run without PQS or a DAR, while an authorized contract track requires explicit participant/PQS rights. A source can feed multiple tracks but never widen the source's visibility. Proof after first release: an independent public-only track plus a private track with distinct source-local cursors and privacy tests. **Deferred by D-006; not a Phase 3 feature.**

**H5 — Complement existing Canton tooling.** PQS owns its own schema/ingestion; CantonGrid reads documented interfaces with least privilege. Evaluate Nodejumper's typed client and, after the interfaces/source license become public, whether Canton Index can serve a projection-adapter role. No requirement to install a competing product or accept a private binary is implied. Record an ADR before changing the architecture; this comparison alone does not authorize a pivot.

| LocalNet / PQS research | **LocalNet-tested upstream helpers:** Canton 3.5.7, Scribe 3.5.4 / schema 041, scoped read-only SQL, source recovery, visibility/precision observations. These are **not live CantonGrid connector tests**. |
| CI | [Latest main workflow](https://github.com/kunal171/cantongrid/actions/runs/44070241204) **passed** on the reviewed commit. Repository verification reports **29 Rust tests** and **6 Python helper regressions**, formatting and Clippy. This review inspected GitHub evidence; it did not rerun the toolchain locally. |
| PostgreSQL destination / generated APIs / streams | **Not implemented:** no owned persistent canonical tables, worker checkpoints/outbox, generated REST/GraphQL, authenticated SSE or production-quality ingestion. |
| Multi-source Scan and other tracks | **Deferred** by accepted decisions D-001/D-006; not part of current release. |

**Stage verdict:** Documentation/research and **Phase 2 fixture milestone complete**; **Phase 3 authorized LocalNet ingestion** is next. There is a credible tested foundation, but **no live end-to-end Rust indexer product yet**. ## Decisions recommended before a grant submission

1. **Preserve the existing contracts-first plan.** Finish real authorized Outcomia and unrelated-package indexing, owned PostgreSQL, atomic checkpoints, auth and API paths before claiming a generalized data platform.
2. **Demonstrate beyond Canton Index M2.** A plain PQS-to-JSONB pipeline now directly competes with its released server. Show a useful declarative derived model, lifecycle-dependent access control, generated API and recovery behavior that its *currently shipped* release does not demonstrate; re-evaluate after its M4 release.
3. **Treat the proposed multi-track capability as a later milestone.** It is a potential differentiator only if a source without Daml/PQS can be added without modifying the core and without weakening privacy semantics.
4. **Prove credibility with two genuine integrations.** Outcomia is the first adopter, but the second unrelated package must run through the same public configuration with no engine changes; seek an external design partner for stronger ecosystem evidence.
5. **Create a reproducible comparison.** Publish release/version matrix, installation steps, source scope, query classes, correctness tests, measured CPU/memory/latency and authorizations before using "better" or "faster". Test competitors only where published artifacts and usage rights permit.
6. **Position it as complementary common-good tooling under [RFP #20 — Indexers](https://github.com/canton-foundation/canton-dev-fund/blob/main/2026-2028-strategic-roadmap.md).** Explicitly explain what PQS, Canton Index, Zpoken and Noves already solve, what CantonGrid contributes separately, the privacy model and the objective milestone evidence. If the gap cannot be demonstrated, consider contributing an interoperable extension to existing infrastructure instead of duplicating it.

These are **research recommendations**, not changes to accepted architecture or release commitments. Any scope change should be recorded as a new explicit decision in [decisions](decisions.md) before implementing it.
